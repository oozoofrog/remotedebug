# 실기기 확인 절차

> **사용자가 직접 승인해야 하는 동작.** 에이전트는 승인 없이 이 동작을 하지 않는다.
>
> - 실제 iPhone에 앱을 설치하거나 지우는 일(D9, 설치 웹 페이지로 설치하는 D14 포함), 기기를 지우고 복원하는 일(D6)
> - Apple Developer 계정 설정 변경(App ID 등록, Network Extension 권한, iPhone 기기 등록)
> - 실제 tailnet에 노드를 추가하거나 관리 콘솔에서 지우는 일, tailnet의 DNS·HTTPS·ACL 설정을 바꾸는 일
> - 사용자의 tailnet을 쓰는 일: 공식 Tailscale 앱으로 iPhone을 그 tailnet에 로그인하고, 그 iPhone 노드를 Mac에서 허용하는 일(D14)
> - Mac 앱의 tailnet 상태 폴더(`state`)를 지우는 일(D9)
> - 인증 키를 만들거나 쓰는 일

아래 기대 결과는 설계상 예상이며, 어느 항목도 아직 확인하지 않음. 결과는 [결과 기록표](device-test-results.md)에 적고, 로그와 스크린샷은 저장소 루트의 `device-evidence/` 폴더에 `<항목 번호>-<순번>.<확장자>` 이름으로 둔다. 이 폴더는 노드 이름과 tailnet 주소를 담을 수 있어 저장소에서 제외했다.

## 시작 전 준비

1. [설정 문서](setup.md)대로 두 앱을 빌드하고 tailnet을 준비한다.
2. iPhone을 Mac에 연결하고 Mac의 콘솔 앱에서 그 iPhone을 고른다.
3. 콘솔 앱의 검색에 `subsystem:com.oozoofrog.app.RemoteDebugPhone`을 넣는다. 터널 확장의 기록은 `com.oozoofrog.app.RemoteDebugPhone.Tunnel`이다. 이 두 값은 코드에 고정돼 있어 번들 ID를 바꿔도 그대로다. 코어 메시지 본문은 `<private>`로 가려질 수 있다.

| 볼 곳 | 위치 | 내용 |
| --- | --- | --- |
| VPN 진단 | iPhone 앱 > 톱니 > 설정 > "VPN 진단" | VPN, tailnet 상태, tailnet 주소, 피어, 경로, MTU, 코어 메모리(RSS), 확장 메모리(phys_footprint), 확장 단계, 마지막 오류 |
| 활동 | Mac 앱 > 활동 > "활동" | 페어링 결과, 설치 진행, 거부된 접근 |
| 코어 로그 | Mac 앱 > 활동 > "코어 로그" | 코어의 경고와 메시지 |
| 네트워크 | Mac 앱 > 네트워크 | 공유 상태, 주소(FQDN), HTTPS 인증서, 고급 > 코어 메모리 |

## 실행 순서

앞 항목이 실패하면 뒤 항목의 결과를 믿을 수 없으므로 이 순서로 진행한다.

| 단계 | 항목 | 이유 |
| --- | --- | --- |
| 1 | U9 | 권한이 없으면 iPhone 앱을 기기에 설치할 수 없다 |
| 2 | D9 | tailnet 로그인 없이는 나머지를 볼 수 없다 |
| 3 | U1, U2 | 터널이 시작되는지 본다 |
| 4 | D2 | Mac의 HTTPS가 있어야 페어링과 설치를 할 수 있다 |
| 5 | U4 | iPhone이 Mac의 이름을 찾아야 한다 |
| 6 | D12, D13, D1 | 페어링, Debug 확인 대화상자(Mac 앱만 있으면 된다), 설치 |
| 7 | D14 | 공식 Tailscale 앱과 Safari로 하는 설치. RemoteDebug iPhone 앱의 VPN을 끄고 한다 |
| 8 | U6, D3 | 메모리 |
| 9 | U5, U3, D4 | 네트워크 전환 |
| 10 | D7, D8, D5, U7 | VPN 끄기와 재시동 |
| 11 | D11 | 기기 제거 |
| 12 | U8, D10 | tailnet 설정을 바꿔야 한다 |
| 13 | D6 | 기기를 복원해야 한다 |

RemoteDebug iPhone 앱 없이 D14만 할 때는 D9의 Mac 부분(공유 시작과 로그인), D2, D13·D1의 Mac 쪽 빌드 가져오기를 마친 뒤 바로 D14를 한다.

## tunnel.md의 실기기 항목

U 번호는 `docs/tunnel.md`의 "실기기에서만 확인할 것" 번호와 같다. 인용문은 그 문서의 문장이다.

### U1. utun fd 탐색과 CreateTUNFromFile

> 1. iOS NE 샌드박스에서 utun fd 탐색과 `CreateTUNFromFile`(UTUN_OPT_IFNAME, `net.InterfaceByName`, AF_ROUTE 소켓)이 되는가. 경로 감시 소켓 오류는 장치 전체를 닫는다(→ `TUN 장치가 닫혔습니다.`).

- 목표: 확장이 utun을 찾아 코어를 시작하는지 본다.
- 절차:
  1. 콘솔 앱에서 기록을 시작한다.
  2. iPhone 앱에서 **VPN 켜기**를 누르고 로그인한다.
  3. 5분 동안 VPN을 켜 둔다.
- 기대 결과: 콘솔에 `utun 확인: <이름> fd=<번호>`와 `코어 시작됨`이 나온다. VPN 진단의 확장 단계가 "실행 중"이고 tailnet 상태가 `Running`이다.
- 기록: 콘솔 기록 파일, VPN 진단 스크린샷.
- 실패 시: "VPN 장치(utun)를 찾지 못했습니다."면 `Apps/iOSTunnel/UTUNLocator.swift`를 본다. "TUN 장치가 닫혔습니다."면 경로 감시 소켓 오류를 의심한다.

### U2. 첫 네트워크 설정 전의 utun

> 2. 첫 `setTunnelNetworkSettings` 전에 utun과 fd가 있는가(없으면 자리표시 설정).

- 목표: 어느 경로로 utun을 얻는지 기록한다.
- 절차:
  1. VPN을 끈 상태에서 콘솔 기록을 시작한다.
  2. **VPN 켜기**를 누른다.
  3. `utun 확인:` 앞에 `utun이 없어 자리표시 설정을 먼저 적용합니다`가 있는지 본다.
- 기대 결과: 두 경우 모두 `utun 확인:`까지 간다. 자리표시 문장 유무가 이 항목의 답이다.
- 기록: 콘솔 기록 파일, 자리표시 문장 유무.
- 실패 시: "VPN 네트워크 설정을 적용하지 못했습니다."면 자리표시 설정(터널 원격 주소와 `mtu`만)을 의심한다.

### U3. 셀룰러의 CGNAT 충돌

> 3. 피어별 /32 경로가 셀룰러에서 통신사 CGNAT 주소와 충돌하지 않는가.

- 목표: 셀룰러에서 tailnet과 일반 인터넷이 함께 되는지 본다.
- 절차:
  1. Wi-Fi를 끄고 셀룰러만 켠다.
  2. **VPN 켜기**를 누르고 연결을 기다린다.
  3. VPN 진단의 경로 수를 적는다.
  4. 앱의 빌드 목록을 새로고침한다.
  5. Safari로 tailnet 밖 사이트를 연다.
- 기대 결과: 목록을 받고 사이트도 열린다.
- 기록: 통신사, 경로 수, 스크린샷. 셀룰러 주소가 `100.64.0.0/10` 안인지는 앱으로 알 수 없으므로, 통신사 정보로 알 수 없으면 비고에 "확인하지 않음"으로 적는다.
- 실패 시: 사이트만 열리지 않으면 경로 충돌을 의심한다.

### U4. 일치 도메인 66개 이상의 DNS

> 4. 일치 도메인 66개 이상 + `matchDomainsNoSearch = true`에서 `<host>.<tailnet>.ts.net`과 PTR이 100.100.100.100으로 풀리는가.

- 목표: iPhone이 Mac의 FQDN과 PTR을 터널로 푸는지 본다.
- 절차:
  1. VPN을 켜고 콘솔에서 `network-settings:` 줄의 `DNS 있음`을 확인한다.
  2. 페어링을 요청하거나 빌드 목록을 새로고침한다. 앱은 Mac의 FQDN으로 접속한다.
  3. PTR은 앱 화면으로 볼 수 없다. DNS 조회 앱을 쓸 수 있으면 Mac의 tailnet IP를 역방향으로 조회한다.
- 기대 결과: FQDN 접속이 된다. PTR 조회에 Mac의 이름이 나온다.
- 기록: `network-settings:` 줄, 조회 결과. PTR을 조회할 도구가 없으면 비고에 "PTR 확인하지 않음"으로 적는다.
- 실패 시: "Mac에 연결할 수 없습니다. iPhone의 VPN이 켜져 있는지, Mac 앱이 공유 중인지 확인하세요."가 나오고 `DNS 없음`이면 MagicDNS 설정을 먼저 본다.

### U5. 확장 소켓의 터널 우회와 인터페이스 전환

> 5. 확장 자신의 제어·DERP·WireGuard 소켓이 터널을 우회하는가, `setDefaultInterface`로 인터페이스 전환을 따라가는가.

- 목표: 터널이 자기 트래픽을 다시 터널로 보내지 않고, 인터페이스 전환 뒤 회복하는지 본다.
- 절차:
  1. Wi-Fi로 VPN을 켜고 tailnet 상태가 `Running`인지 본다.
  2. Wi-Fi를 끈다. tailnet 상태가 다시 `Running`이고 빌드 목록을 새로 받을 때까지 시간을 잰다.
  3. Wi-Fi를 켜고 같은 시간을 잰다.
- 기대 결과: 상태가 멈추지 않고 돌아오며 앱을 다시 시작하지 않아도 목록을 받는다.
- 기록: 전환 방향별 회복 시간(초), 콘솔 기록 파일.
- 실패 시: `Running`으로 돌아오지 않으면 `setDefaultInterface` 호출과 소켓 묶임을 의심한다.

### U6. 확장의 메모리 한도

> 6. 확장 전체(Go + Swift + NE 프레임워크)의 phys_footprint가 유휴·트래픽 상태에서 50MiB 안인가.

- 목표: 확장 메모리가 보고된 한도 안에 드는지 본다.
- 절차: 아래 D3의 절차대로 잰다.
- 기대 결과: 유휴와 전송 중 모두 확장 메모리(phys_footprint)가 50MiB 미만이다.
- 기록: [결과 기록표](device-test-results.md)의 "D3 메모리" 표.
- 실패 시: D3 참조.

### U7. 첫 잠금 해제 전 시작

> 7. 첫 잠금 해제 전 주문형 VPN 시작에 맞는 `stateDir`의 데이터 보호 등급·App Group 위치.

- 목표: 첫 잠금 해제 전 시작이 가능한지 본다.
- 현재 코드: 앱은 주문형(On Demand) 규칙을 설정하지 않고, App Group도 쓰지 않는다. `stateDir`는 확장 컨테이너의 `Library/Application Support/RemoteDebug/tailscale`이고 보호 등급은 `completeUntilFirstUserAuthentication`이다.
- 절차:
  1. VPN을 켜고 VPN 진단의 tailnet 주소를 적는다.
  2. iPhone을 재시동하고 잠금을 해제한다.
  3. 앱을 열어 **VPN 켜기**를 누른다.
- 기대 결과: 로그인을 다시 묻지 않고 같은 tailnet 주소가 나온다.
- 기록: 재시동 전후 tailnet 주소. 주문형 규칙이 없어 잠금 해제 전 시작은 시험할 수 없으므로 결과는 "해당 없음", 비고에 "주문형 규칙 없음"으로 적는다.
- 실패 시: 로그인을 다시 물으면 `stateDir`의 보호 등급과 위치를 의심한다.

### U8. 기본 리졸버를 쓰려는 tailnet의 DNS

> 8. iOS에서 엔진이 100.100.100.100을 기본 리졸버로 삼으려는 tailnet(사용자 지정 서버로 가는 split DNS, 역방향 영역 밖 주소의 ExtraRecord, `DisableSplitDNSWhenNoCustomResolvers` 노브)에서도 범위 지정 DNS가 나가는 것은 Go 테스트(`TestTunnelIOSDNS`, goos `ios`)로 확인했다. 실기기에서는 그런 tailnet에서 호스트 FQDN이 풀리고 다른 이름(인터넷 이름, `corp.example.com`)은 기기 리졸버로 풀리는지만 본다.

- 목표: 사용자 지정 DNS가 있는 tailnet에서 기기의 일반 DNS가 유지되는지 본다.
- 절차:
  1. 사용자 승인을 받아 tailnet DNS 페이지에 사용자 지정 서버로 가는 split DNS를 추가한다.
  2. VPN을 다시 켠다.
  3. 빌드 목록을 새로고침한다.
  4. Safari로 인터넷 사이트를 연다.
  5. split DNS에 넣은 도메인의 이름이 기기 리졸버로 풀리는지 DNS 조회 앱으로 본다.
  6. 추가한 설정을 지운다.
- 기대 결과: 목록을 받고 인터넷 이름이 풀린다. split DNS 도메인은 터널로 풀리지 않는다.
- 기록: 추가한 설정, 콘솔의 `network-settings:` 줄, 조회 결과.
- 실패 시: 인터넷 이름이 풀리지 않으면 `dnsMatchDomains` 범위 한정을 의심한다.

### U9. Network Extension 권한

> 9. 사용 중인 개발자 계정에서 Network Extension 권한을 쓸 수 있는가.

- 목표: 계정에서 앱을 서명할 수 있는지 본다.
- 절차:
  1. `Config/Signing.local.xcconfig`에 팀 ID를 넣고 `xcodegen generate --spec project.yml`을 실행한다.
  2. Xcode에서 `RemoteDebugPhone`과 `RemoteDebugTunnel`의 Signing & Capabilities를 연다.
  3. 사용자 승인을 받아 App ID 등록과 권한 추가를 진행한다.
- 기대 결과: 두 대상 모두 프로필 오류 없이 Network Extensions(Packet Tunnel)가 표시된다.
- 기록: Signing & Capabilities 스크린샷, 계정 종류(개인·조직, 무료·유료).
- 실패 시: 권한을 지원하지 않는다는 오류면 그 계정으로는 iPhone 앱을 만들 수 없다. [판정서](appstore-review.md)의 배포 대안을 본다.

## 추가 항목

### D1. OTA 설치

- 목표: iOS 설치기가 터널로 Mac에서 앱을 받아 설치하는지 본다.
- 절차:
  1. 공식 Tailscale 앱이 있으면 그 앱의 VPN을 끈다.
  2. iPhone의 설정 > 개인정보 보호 및 보안 > 개발자 모드를 켠다.
  3. 그 iPhone이 프로필에 들어 있는 앱을 Xcode에서 Debug 구성, 기기용으로 빌드한다.
  4. Mac 앱에서 가져와 "게시된 빌드"에 있는지 본다.
  5. iPhone 앱에서 **설치**를 누른다.
  6. iOS 설치 창이 뜨면 취소해서 닫는다. "iOS 설치 창에서 ‘설치’를 누르세요"와 **다시 열기**, **취소**가 남아 있는지 본다.
  7. **다시 열기**를 눌러 창을 다시 띄우고 설치를 누른다.
  8. "전송 완료" 뒤 홈 화면에서 앱을 연다. 개발자를 신뢰하라는 알림이 나오면 설정 > 일반 > VPN 및 기기 관리에서 신뢰한 뒤 다시 연다.
- 기대 결과: Mac 활동에서 그 세션의 줄 하나가 "<노드 이름> · <빌드 이름>: 설치 정보 전송" → "내려받는 중" → "설치 파일 전송 완료"로 바뀌고 앱이 실행된다. 세션마다 줄은 하나라서 앞 단계 문구는 남지 않는다.
- 기록: Mac 활동 화면 녹화(줄이 바뀌는 모습), iPhone 화면 녹화, 빌드 크기와 전송 시간.
- 실패 시: 전송이 시작되지 않으면 U4와 D2를 먼저 본다. 매니페스트는 세션마다 5번까지 받을 수 있어 **다시 열기**를 반복하면 끊길 수 있다. 앱이 실행되지 않으면 개발자 모드와 프로필의 기기 등록을 본다.

### D2. 실제 TLS 인증서

- 목표: 인증서 발급 시간과 HTTPS 제공을 잰다.
- 절차:
  1. Mac 앱에서 **공유 시작**을 누른 시각을 적는다.
  2. 상태가 "인증서 발급 중"에서 "공유 중"으로 바뀐 시각을 적는다.
  3. 네트워크 화면의 "HTTPS 인증서"가 "발급됨"인지 본다.
  4. 이미 tailnet에 있는 다른 기기에서 `curl -v https://<FQDN>/v1/info`를 실행한다.
- 기대 결과: 인증서 검증이 통과하고 페어링하지 않은 기기는 403 `not_paired`를 받는다.
- 기록: 발급 시간(초), `curl` 출력의 인증서 부분과 상태 코드.
- 실패 시: 코어는 인증서를 받을 때까지 30초, 60초, 120초(최대 10분) 간격으로 다시 시도한다. 10분이 넘으면 코어 로그와 D10을 본다.

### D3. VPN 메모리

- 목표: 터널 확장의 메모리를 상태별로 잰다. 한도는 Apple 포럼 보고치인 약 50MiB로 가정하며, 코어의 `goMemLimitMiB`는 28이다.
- 절차:
  1. VPN을 켜고 10분 동안 유휴로 둔다. 앱을 앞에 띄운 채 VPN 진단의 코어 메모리(RSS)와 확장 메모리(phys_footprint)를 적는다.
  2. Xcode의 Debug > Attach to Process에서 `RemoteDebugTunnel` 프로세스에 붙이고 Debug 내비게이터의 메모리 게이지를 본다.
  3. 가장 큰 빌드를 설치하면서 최댓값을 적는다.
  4. Wi-Fi와 셀룰러를 전환하면서 최댓값을 적는다.
- 기대 결과: 모든 값이 50MiB 미만이다.
- 기록: [결과 기록표](device-test-results.md)의 "D3 메모리" 표에 상태(유휴, 전송, 전환)별 RSS, phys_footprint, Xcode 게이지 값(MiB)과 빌드 크기를 적는다.
- 실패 시: VPN이 갑자기 끊기고 "VPN 연결이 끊겼습니다. 다시 연결하세요."가 나오면 메모리 초과 종료를 의심한다. 설정 > 개인정보 보호 및 보안 > 분석 및 향상 > 분석 데이터에서 `JetsamEvent` 기록을 찾는다.

### D4. 네트워크 전환

- 목표: 전송 중 Wi-Fi·셀룰러 전환의 영향을 본다.
- 절차:
  1. Wi-Fi로 연결하고 빌드 설치를 시작한다.
  2. 전송 중 Wi-Fi를 끈다.
  3. 전송이 이어지는지, 실패 문구가 나오는지 본다. 끊긴 전송은 설치 줄이 "전송 중"으로 남을 수 있다. Mac 세션은 시간으로만 만료되고, iPhone은 **설치**를 누른 뒤 600초가 지나야 이 설치를 끝난 것으로 처리한다.
  4. 다시 Wi-Fi를 켠다. 전송이 이어지지 않으면 설치 줄에 "설치 세션이 만료되었습니다. 다시 설치하세요." 같은 만료·실패 문구와 **다시 설치**가 나올 때까지 기다린 뒤 눌러 끝까지 받는다.
- 기대 결과: 터널은 회복한다. 전송이 끊기면 최대 600초 뒤 **다시 설치**로 끝낼 수 있다.
- 기록: 전환 시각, 앱 문구, 회복 시간, **다시 설치**가 나온 시각.
- 실패 시: U5를 본다.

### D5. 잠금과 재시동 뒤 재연결

- 목표: 잠금과 재시동 뒤 VPN 상태를 본다.
- 절차:
  1. VPN을 켜고 iPhone을 잠근 채 10분 둔다.
  2. 잠금을 풀고 앱을 열어 상태와 목록을 본다.
  3. iPhone을 재시동하고 잠금을 푼 뒤 앱을 연다.
  4. 꺼져 있으면 **VPN 켜기**를 누른다.
- 기대 결과: 잠금 뒤에는 "연결됨"이다. 주문형 규칙이 없으므로 재시동 뒤에는 꺼져 있고, 켜면 로그인 없이 연결된다.
- 기록: 단계별 VPN 상태, tailnet 상태, tailnet 주소.
- 실패 시: 로그인을 다시 물으면 U7을 본다.

### D6. 백업에서 복원

- 목표: 복원 뒤 다시 로그인과 페어링을 해야 하는지 본다.
- 절차:
  1. 페어링을 마친 iPhone을 백업한다.
  2. 사용자 승인을 받아 기기를 지우고 백업에서 복원한다.
  3. 앱이 없으면 Xcode로 다시 설치한다.
  4. **VPN 켜기**를 누른다.
  5. 로그인한 뒤 빌드 목록을 새로고침한다.
  6. Mac에서 새 코드를 열어 다시 페어링한다.
- 기대 결과: 터널 상태 폴더가 백업에서 빠져 있어 tailnet 로그인을 다시 요구한다. 새 노드는 허용 목록에 없어 "이 iPhone은 Mac에서 승인되지 않았습니다. 다시 페어링하세요."가 나온다. 다시 페어링하면 목록을 받는다.
- 기록: 복원 전후의 tailnet 주소, 앱 문구, Mac 활동.
- 실패 시: 로그인 없이 연결되면 `Apps/iOSTunnel/Shared/TunnelStorage.swift`의 백업 제외를 의심한다.

### D7. 설정과 제어 센터에서 VPN 끄기

- 목표: 앱 밖에서 끈 VPN을 앱이 오류로 다루지 않는지 본다.
- 절차:
  1. VPN을 켠다.
  2. 설정 > VPN에서 끄고 앱을 연다.
  3. 다시 켠 뒤 제어 센터의 VPN 제어로 끄고 앱을 연다. 제어 센터에 VPN 제어가 없으면 비고에 적는다.
- 기대 결과: VPN 카드가 "꺼짐"이고 "다시 연결"이나 오류 문구가 나오지 않는다.
- 기록: 경로별 스크린샷.
- 실패 시: "VPN 연결이 끊겼습니다. 다시 연결하세요."가 나오면 `Apps/iOS/Adapters/TunnelStateMapping.swift`의 `disconnectMessage`를 본다.

### D8. 시작 중 VPN 끄기

- 목표: 시작 도중의 끄기가 노드를 남기지 않는지 본다.
- 절차:
  1. 콘솔 기록을 시작한다.
  2. **VPN 켜기**를 누르고 "연결 중"일 때 **VPN 끄기**를 누른다.
  3. 같은 순서를 설정 > VPN의 끄기로 반복한다.
  4. 꺼진 뒤 **VPN 켜기**를 눌러 정상 연결을 본다.
- 기대 결과: 오류 없이 "꺼짐"이 된다. 다음 켜기가 된다. 콘솔에 `시작 중 종료 요청을 받아 새 노드를 멈춥니다`가 나올 수 있다.
- 기록: 콘솔 기록 파일, 각 시도의 최종 상태.
- 실패 시: 다음 켜기가 `state_dir_in_use`나 `tunnel_in_use`로 실패하면 앞 노드가 남은 것이다.

### D9. 브라우저와 인증 키 로그인

- 목표: 두 앱에서 두 로그인 방법을 본다.
- 절차:
  1. Mac: **공유 시작** 뒤 **로그인 페이지 열기**로 로그인한다.
  2. iPhone: **VPN 켜기** 뒤 **로그인 페이지 열기**로 로그인한다.
  3. 사용자 승인을 받아 두 기기의 로그인 상태를 지운다.
     - tailnet 관리 콘솔의 Machines에서 두 노드를 지운다. 지운 노드는 다시 로그인할 때까지 tailnet에 연결하지 못한다.
     - Mac: RemoteDebug를 종료하고 `~/Library/Containers/com.oozoofrog.app.RemoteDebugMac/Data/Library/Application Support/RemoteDebug/state` 폴더만 지운다. Mac의 tailnet 노드 키가 지워진다. 그 위 `RemoteDebug` 폴더의 `devices.json`(허용 기기 목록), `builds.json`(빌드 목록), `Published/`(게시한 IPA), `identity.json`(노드 이름의 8자)은 지우지 않는다. 이 파일들까지 지우면 허용 기기와 게시한 빌드가 사라지고 Mac 노드 이름이 바뀐다.
     - iPhone: 앱을 지우고 Xcode로 다시 설치한다. tailnet 로그인과 저장한 Mac 페어링이 함께 지워지므로 D9 뒤에 다시 페어링한다.
  4. 사용자 승인을 받아 인증 키를 만든다.
  5. Mac: **네트워크** 화면의 "인증 키(선택)"에 키를 넣고 **공유 시작**을 누른다. iPhone: **인증 키로 켜기**를 누르고 키를 넣는다.
  6. 앱을 다시 시작해 키를 다시 묻지 않는지 본다.
  7. 잘못된 키로 한 번 시도한다.
- 기대 결과: 네 경우 모두 연결된다. 키는 입력란에 남지 않는다. 잘못된 키는 Mac에서 "공유 오류", iPhone에서 "tailnet에 연결하지 못했습니다. ‘다시 연결’을 누르고, 계속되면 ‘인증 키로 켜기’로 다시 로그인하세요."로 나온다.
- 기록: 방법별 결과, 로그인에서 연결까지의 시간. 인증 키 자체는 기록하지 않는다.
- 실패 시: "tailnet 로그인 주소를 받는 중입니다."에 멈추면 코어의 로그인 재시도(30초에 한 번)와 네트워크를 본다.

### D10. HTTPS가 꺼진 tailnet

- 목표: "HTTPS 인증서 꺼짐" 안내의 "켜면 공유를 다시 시작하지 않아도 잠시 뒤 설치 주소가 열립니다."가 맞는지 본다.
- 절차:
  1. 사용자 승인을 받아 DNS 관리 페이지에서 HTTPS Certificates를 끈다.
  2. Mac 앱에서 공유를 다시 시작하고 "HTTPS 인증서 꺼짐"이 나오는지 본다. **iPhone 페어링…**을 누를 수 없어야 한다.
  3. **DNS 설정 페이지 열기**로 들어가 HTTPS Certificates를 켠다. 앱은 건드리지 않고 시각을 적는다.
  4. 상태가 "공유 중"이 될 때까지 기다린다.
- 기대 결과: 다시 시작 없이 "공유 중"이 된다.
- 기록: 켠 시각에서 "공유 중"까지의 시간, 전후 스크린샷.
- 실패 시: 10분 안에 바뀌지 않으면 안내 문구가 틀린 것이다. 공유를 다시 시작해서 풀리는지도 적는다.

### D11. 기기 제거와 이어지는 거부

- 목표: 제거한 기기가 곧바로 막히는지 본다.
- 절차:
  1. iPhone에서 설치를 시작해 전송 중으로 둔다.
  2. Mac의 기기 화면에서 그 기기의 **제거**를 누르고 대화상자에서 **제거**를 누른다.
  3. iPhone에서 전송 결과를 본다.
  4. iPhone에서 빌드 목록을 새로고침한다.
- 기대 결과: 전송이 끊기고 설치 줄에 "이 iPhone은 Mac에서 승인되지 않았습니다. 다시 페어링하세요."가 나온다. 제거된 기기는 세션 상태 조회도 403 `not_paired`로 거부되기 때문이다. 새로고침해도 같은 문구가 나온다. Mac 활동에서 그 세션의 줄은 "실패"로 바뀌고, 제거 뒤의 요청은 거부 기록으로 남는다.
- 기록: iPhone 스크린샷, Mac 활동 스크린샷.
- 실패 시: 목록을 계속 받으면 허용 목록 반영을 의심한다. 코어 로그를 본다.

### D12. 페어링 코드 다섯 번 틀리기

- 목표: 코드 폐기와 Mac 화면의 표시를 본다.
- 절차:
  1. Mac에서 **iPhone 페어링…**을 눌러 코드를 연다.
  2. iPhone에서 Mac 주소와, Mac의 코드와 다른 8자 코드를 넣고 **페어링 요청**을 누른다. 코드는 영문 대문자와 숫자로 만들고 `U`는 넣지 않는다(`U`가 든 코드는 iPhone이 보내지 않아 횟수에 들지 않는다). 누를 때마다 입력 화면이 잠시 사라졌다가 빈 채로 다시 나타나므로, Mac 주소와 코드를 다시 넣어 모두 다섯 번 보낸다.
  3. 여섯 번째로 맞는 코드를 넣는다.
  4. Mac의 시트가 언제 "코드가 만료됐거나 틀린 시도가 많아 더 쓸 수 없습니다. 새 코드를 만드세요."로 바뀌는지 본다.
  5. **새 코드 만들기**로 새 코드를 열어 페어링을 끝낸다.
- 기대 결과: 다섯 번은 "페어링 코드가 맞지 않거나 만료되었습니다. Mac에 표시된 코드를 확인하고 다시 입력하세요."이고, 여섯 번째는 맞는 코드여도 "코드를 너무 많이 틀렸습니다. Mac에서 새 페어링 코드를 연 뒤 다시 시도하세요."다. `denied` 이벤트가 5초에 하나로 제한되어 Mac은 폐기된 코드를 다음 이벤트까지 보여 줄 수 있다.
- 기록: 시도별 문구와 시각, Mac 시트가 바뀐 시각.
- 실패 시: 여섯 번째에 맞는 코드가 통과하면 코어의 폐기 처리를 의심한다.

### D13. Debug 확인 대화상자

- 목표: Debug 구성을 폴더 이름과 `*.debug.dylib` 어느 쪽으로도 증명하지 못하는 빌드를 가져올 때, 대화상자가 뜨고 사용자가 확인한 그 내용만 게시되는지 본다. 이 경로는 다른 항목이 거치지 않는다(D1의 `Debug-iphoneos` 폴더 빌드는 대화상자 없이 수락된다).
- 준비: 기기용 Debug 빌드를 `Debug-iphoneos`가 아닌 이름의 폴더에 두고 앱 안에 `*.debug.dylib`가 없게 만든다. 예: `xcodebuild`에 `CONFIGURATION_BUILD_DIR=<임의 폴더>`와 `ENABLE_DEBUG_DYLIB=NO`를 준다. 이 설정으로 대화상자가 뜨는지도 확인 대상이다.
- 절차:
  1. Mac 앱에서 **빌드 가져오기…**로 그 `.app`을 고른다.
  2. 대화상자 제목이 "Debug 구성으로 빌드한 앱인가요?"이고 본문 첫 줄이 `번들 ID 버전 (빌드 번호)`, 둘째 줄이 그 앱의 경로인지 본다.
  3. **가져오지 않기**를 누른다. 빌드 목록에 오르지 않아야 한다.
  4. 같은 앱을 다시 가져와 이번에는 **Debug 빌드로 가져오기**를 누른다. 게시되고 구성 증거가 "Debug · 직접 확인"으로 보여야 한다.
  5. 앱을 다른 빌드(버전이나 빌드 번호가 다른 것)로 바꿔 다시 가져온다. 대화상자가 떠 있는 동안 같은 경로에 그 다른 빌드를 덮어쓰고 **Debug 빌드로 가져오기**를 누른다.
- 기대 결과: 5단계에서 게시되지 않고 "<이름>: 확인한 뒤 내용이 바뀌어 가져오지 않았습니다. 다시 가져와 새 내용을 확인하세요."가 나온다. `.app`은 파일 메타데이터가, `.ipa`는 SHA-256이 같아야 확인한 내용으로 본다.
- 기록: 단계별 스크린샷, 빌드 목록.
- 실패 시: 대화상자 없이 수락되면 폴더 이름이나 `*.debug.dylib`가 증거로 남아 있는 것이다. 5단계에서 게시되면 확인과 내용의 묶음을 의심한다.

### D14. 설치 웹 페이지(공식 Tailscale 앱)

- 목표: RemoteDebug iPhone 앱 없이, 공식 Tailscale 앱을 켠 iPhone이 Safari로 Mac의 설치 웹 페이지를 열어 페어링하고 Debug 빌드를 설치하는지 본다. 실제 TLS, 공식 앱 노드의 접속, Safari에서 여는 `itms-services` 설치 창을 처음 확인하는 항목이다.
- 준비: [설정 문서의 웹 페이지 절](setup.md#iphone에서-앱-없이-설치웹-페이지)에 있는 준비 항목을 마친다. 사용자 승인을 받아 공식 Tailscale 앱으로 iPhone을 Mac과 같은 tailnet에 로그인한다. RemoteDebug iPhone 앱이 있으면 그 앱의 VPN을 끈다. Mac에는 그 iPhone이 프로필에 들어 있는 Debug 빌드를 게시해 둔다.
- 절차:
  1. Mac **네트워크** 화면의 "HTTPS 인증서"가 "발급됨"이고 "설치 페이지" 줄에 주소가 있는지 본다.
  2. Mac **기기** 화면에서 **iPhone 페어링…**을 누르고, 시트에 "앱 없이 Safari로 설치"의 QR, 링크, **링크 복사**가 있는지 본다.
  3. iPhone 카메라로 그 QR을 찍어 Safari에서 연다. 카메라로 열 수 없으면 **링크 복사**로 보낸 링크를 Safari에서 열고, 어느 방법을 썼는지 적는다.
  4. Safari에 인증서 경고 없이 "Mac 페어링" 입력 화면이 나오고 "페어링 코드" 칸에 시트의 코드가 들어 있는지 본다.
  5. "기기 이름"을 다른 기기와 구별되는 이름으로 바꾸고 **페어링 요청**을 누른다.
  6. Mac 시트의 요청 줄에서 기기 이름, 괄호 안의 노드 이름, tailnet 로그인 이름을 적는다. 노드 이름을 tailnet 관리 콘솔의 Machines 목록에 있는 그 iPhone의 이름과 비교한 뒤 **허용**을 누른다.
  7. 페이지가 "빌드" 목록으로 바뀌는지 본다.
  8. 빌드의 **설치**를 누르고 **설치 창 열기**를 누른다. iOS 설치 창이 뜨면 취소해서 닫고, 같은 자리에 **다시 열기**가 있는지 본다.
  9. **다시 열기**를 눌러 창을 다시 띄우고 설치를 누른다.
  10. "전송 완료" 뒤 홈 화면에서 앱을 연다. 개발자를 신뢰하라는 알림이 나오면 설정 > 일반 > VPN 및 기기 관리에서 신뢰한 뒤 다시 연다.
  11. Mac **기기** 화면에서 6단계에서 허용한 기기를 **제거**한다. 페이지의 **새로고침**을 눌러 "Mac 페어링" 입력 화면이 나오는지 본다. Mac에서 새 코드를 열어 그 코드로 다시 **페어링 요청**을 누르고, 이번에는 Mac에서 **거부**를 누른다.
  12. iPhone 공식 Tailscale 앱의 VPN을 끄고 페이지를 새로고침해, Safari가 페이지를 열지 못하는지와 그때의 Safari 문구를 적는다.
- 기대 결과: 4단계의 페이지가 인증서 경고 없이 열린다. 6단계 요청 줄의 노드 이름은 `rd-phone-<8자>`가 아닌 그 iPhone의 노드 이름이다. 8~9단계에서 Mac 활동의 그 세션 줄이 "<노드 이름> · <빌드 이름>: 설치 정보 전송" → "내려받는 중" → "설치 파일 전송 완료"로 바뀌고, 앱이 실행된다. 11단계에서 새로고침 뒤에는 "이 iPhone은 Mac에서 승인되지 않았습니다. 다시 페어링하세요."가, 거부 뒤에는 "Mac에서 페어링을 거절했습니다. 다시 하려면 Mac에서 새 코드를 여세요."가 나온다. 모두 설계상 예상이며 확인하지 않음.
- 기록: Safari 화면 녹화(입력, 대기, 목록, 설치), Mac 시트의 요청 줄 스크린샷(노드 이름이 보이게), Mac 활동 화면 녹화, iOS 버전, 공식 Tailscale 앱 버전, 3단계에서 쓴 방법, 빌드 크기와 전송 시간, 12단계의 Safari 문구.
- 실패 시: 페이지가 열리지 않으면 공식 앱의 VPN과 로그인한 tailnet, tailnet 정책([tailnet 정책(ACL)](setup.md#tailnet-정책acl)), D2를 본다. 인증서 경고가 나오면 D2를 본다. 설치 창이 뜨지 않고 Mac 활동이 "설치 정보 전송"으로 바뀌지 않으면 Safari가 `itms-services` 링크를 열지 않은 것으로 보고 D1과 비교한다. "설치 정보 전송"까지 가고 멈추면 D1의 실패 시 항목을 본다. 앱이 실행되지 않으면 개발자 모드와 프로필의 기기 등록을 본다.
